# P0 UI/UX fixes: four defects (spec)

Status: draft for the builder's approval (2026-11-27). Feature freeze 2026-11-30, deadline 2026-12-02 23:59 UTC.
Source: the UI/UX review of 2026-11-27 (screenshots `review-ui/home-desktop.png`, `review-ui/home-mobile-top.png`,
`review-ui/home-diagram.png`, `.playwright-mcp/ux3/t6-report.png`). Only the four defects below are in scope.

| # | Defect | Tier | Ledger |
|---|---|---|---|
| D1 | The homepage flow diagram is broken (labels on the arrows, no arrowheads, unreadable at 390 px) | Low | presentation only |
| D2 | The homepage has no navigation on phones (the section links are `display: none` below 900 px) | Low | presentation only |
| D3 | The incident report prints the raw template summary (wei amounts, duplicated address, "Template" tag) | Low | rendering only; the signed body is unchanged |
| D4 | A browser without the wallet has no way to restore access from the recovery code | High | signs and broadcasts a withdrawal on diana |

Everything else from the review (token-bar legend, time formats, auto-lock, CSP/compression, unauthenticated reads,
bundle splitting) is a separate spec and out of scope here.

## Shared rules

- Every file stays in English (comments included). Do not add a runtime dependency.
- TDD for every new pure function: red test first, then the code. The dashboard's vitest runs `src/**/*.test.ts` in a
  node environment with no DOM, so DOM behaviour is verified by the build plus the manual checks written below. Do not
  add a DOM test harness in this task.
- No contract change and no message-encoding change, so no new QCAI stage. D4 must keep the shared TS↔Solidity
  withdrawal vector green (`pnpm -F core test`).
- `pnpm -F dashboard test`, `pnpm -F dashboard build`, `pnpm -F @qday/hosted test` green after each defect.

## D3. The incident report prints the raw template summary

### Current behaviour

`components/IncidentReport.tsx:106-110` renders, unconditionally:

```tsx
Agent's summary <span className="tag">{i.summarySource === "llm" ? "Written by AI" : "Template"}</span>
<p className="wrap-any">{i.summary}</p>
```

`.playwright-mcp/ux3/t6-report.png` (Task 12 owner `0x337a…56b6`) shows what that produces:

> Outbound transfer of 1000000000000000000000 (token 0x8478737e5ac2c2cbf70aad17f459d1b8ab8a7a14) to
> 0x255Fab9c7a2d2D122AC7dCa6FD6906E5bC5e75E7 in tx 0xcca2ea755557c02530413ba3ac02ea68d683797373a229240b5c5a9a64392704
> triggered a rescue: recipient 0x255Fab… is not in the allowlist … Rescued 3 of 3 token balance(s) into the vault.

`apps/agent/src/report.ts` `templateSummary(f, labels)` already writes "10 fUSD sent to 0x255F…75E7" **when it receives
`labels`**, and `apps/agent/src/index.ts:159` always passes `labels: tokenLabels` — so newer reports read fine. The reports
already on chain/disk were produced before that, and their bytes are signed and cannot be rewritten. The renderer must
therefore handle both, which is exactly what it does not do today.

### Change

**a. Pure predicate** in `lib/explain.ts`:

```ts
/** The report's own summary, shown only when it reads as prose. The deterministic template is a machine sentence (raw
 *  wei, full addresses) and the printed claim above already says the same thing in plain words. Never rewrites the
 *  signed body. */
export function reportSummary(i: Incident): string | null {
  const s = typeof i.summary === "string" ? i.summary.trim() : "";
  if (i.summarySource !== "llm") return null;
  if (s.length < 40) return null;
  if (/\d{15,}/.test(s)) return null; // base units, not a human amount
  if (/0x[0-9a-fA-F]{40}/.test(s)) return null; // a full address: the LLM echoed a field
  return s;
}
```

The two content guards are not about `summarySource`: an LLM reply that echoes raw fields is just as unreadable, and the
signed body is the same either way.

**b. Renderer** (`IncidentReport.tsx`):

```tsx
const summary = reportSummary(i);
...
{summary ? (
  <div className="agent-note">
    <div className="lbl">The Guardian's summary <span className="tag">Written by AI</span></div>
    <p className="wrap-any">{summary}</p>
  </div>
) : null}
```

- No summary block at all for a template report. Nothing is lost: the `h2` headline and the `inc-sub` paragraph are
  already `describeIncident()` (plain words from the signed fields), and the stats and timeline carry the amounts,
  blocks and hashes.
- The "Template" tag disappears with it; a tag that names an internal fallback on the screen the user opens after losing
  money is noise.
- Keep "Written by AI" for real LLM prose: the award entry claims honest AI disclosure, and this is where it belongs.

**c. Copy** (one line, same block): the label changes from `Agent's summary` to `The Guardian's summary`, matching the
rest of the app (`Your Guardian is watching`, `the Guardian reports …`). Avoid the possessive "Guardian's Guardian"
problem: the string is exactly `The Guardian's summary`.

|---|---|

| template summary with labels ("10 fUSD sent to 0x255F…75E7") | `null` — the block stays hidden, the prose above is enough |

## D4. Restore access from the recovery code alone

### Current behaviour

Setup tells the user that the recovery code is the only way to get tokens out of the vault
(`lib/setup.ts` `CODE_POWER`, and the FAQ "Is my recovery code stored anywhere?"). But every path into the app needs the
browser wallet:

- `App.tsx` `useStoredOwner()` reads `loadSeed()`; with no seed the stage is `visitor` and every route resolves to
  `/home` or `/setup` (`lib/appState.ts`).
- `session.providePqc()` throws `"wallet is locked"` without a decrypted seed, and `requireKeys("pqc")` only unlocks an
  existing seed.
- `vaultWithdraw.withdrawFromVault()` takes a `UnifiedAccount` and sends the transaction from the owner's own EVM key.

So a lost browser = lost account, even though the *withdrawal signature* is enough on chain: the vault accepts
`withdraw(to, token, amount, sig)` from anyone, and the ML-DSA-87 key comes from the code alone
(`docs/THREAT_MODEL.md` T27). The homepage currently admits this: the FAQ says "Recovery on a new device is on the
roadmap."

### Design

Three parts, in this order.

**4A. A restore screen that needs no wallet** (dashboard: screens and chain reads, nothing signed yet).

Route `#/restore`, reachable at **any** stage (including `visitor`, before a wallet exists), in `FocusShell` like Setup:

- `lib/appState.ts`: add `"restore"` to `HOSTED_SCREENS` and `RouteId`; in `resolveRoute` return `"restore"` **before**
  the `stage === null` guard, so it also works while the wallet check is in flight.
- `App.tsx`: `if (active === "restore") return <FocusShell><ScreenBoundary resetKey="restore"><Restore /></ScreenBoundary></FocusShell>;`
  before the `stage === null` loading branch.
- Entry points: a link under the wallet form in Setup step 1 ("Lost this browser? Use your recovery code"), and a link
  in the homepage FAQ answer ("What if I lose this browser?").

Screen, three steps, no app navigation:

1. **Who and what.** An account address (`0x…`) and the recovery code (`QRC1-…`), or drop the `.txt` that Setup
   downloaded and parse both. Sizes: the file is under 2 KiB; refuse above 64 KiB like `Recover.tsx` does.
2. **Checks, before anything is signed** (all read from the chain, none from the agent's `/config`):
   - the code parses and its derived public key matches the account's registered ML-DSA-87 key
     (`readPqcStatus(account)` + `pqcStatusPublicKey`, the same comparison `session.providePqc` makes);
   - the account has a vault: `hosted.owner(account).vault` first (one request, works for a retired owner), else the
     same creation-address probe `locateVault` uses (`onboard.ts:186-192`) over `txCount(account)` nonces, capped by
     the same `VAULT_PROBE_NONCES`, accepting the first address whose `vault.owner()` is the account. A new
     `findOwnerVault(account, deps)` in `lib/restore.ts`: `locateVault` cannot be reused as is because it also matches
     the guardian, and a restore does not know the guardian;
   - `vault.owner() === account` (never trust the address alone);
   - the vault's balances for fUSD/fETH/fBTC.
3. **Withdraw.** Token, amount, recipient; refuse the owner, the vault and the zero address (`checkWithdraw` in
   `lib/vaultForm.ts` already encodes these). Then sign in the browser and submit.

**4B. Sign with the code-derived key** (dashboard, High tier — it signs).

- New pure module `lib/restore.ts` (tested) plus the screen. Derive once with
  `pqcKeyFromRecoveryCode(normalizeRecoveryCode(code))` and pass it to the **existing** signer:
  `signWithdrawalInBrowser({ pqc }, { vault, to, token, amount, nonce }, status)` — it only reads `acc.pqc` and it calls
  `assertRegisteredKey(status, acc.pqc.publicKey)` before signing, which is the guarantee that the key on the chain is
  the one that signs. **Explore first:** confirm in the `@qorechain/sdk@0.14.0` typings that `pqcKeyFromRecoveryCode`
  returns the `{ publicKey, secretKey }` shape `UnifiedAccount["pqc"]` expects; if it returns a different container, wrap
  it rather than touching the signer.
- `pqc.secretKey.fill(0)` in a `finally`, and never store the code or the key (`session` stays untouched: do **not**
  put the derived key into `appSession`, and do not relax `providePqc`'s seed requirement).
- No window, no key of the account's own: the user has neither. Signing is offline.

**4C. Sponsored submit** (hosted service, High tier — it broadcasts).

`POST /api/recover/submit`, body = the seven fields `{ owner, vault, to, token, amount, nonce, sig }` as decimal strings
for the bigints, the same shape `withdrawal.json` carries (`lib/withdrawal.ts` `parseWithdrawalJson`). No owner signature
wrapper: **the withdrawal signature is the authority**, and it binds chain, vault, recipient, token, amount and nonce.

Server order (each step before the next, nothing sent until all pass):

1. shape (0x addresses, `amount > 0`, 4627-byte sig, `to` not zero).
2. `vault.owner() === owner`, read on diana.
3. recompute `withdrawalMessage({ chainId: 9800, vault, to, token, amount, nonce })` from `@qday/core` and require it to
   equal `vault.withdrawalMessage(to, token, amount, nonce)` byte for byte (the shared vector already guards this).
4. `pqcVerify(registeredKey(owner), message, sig)` and `possessionProven === true`.
5. `nonce === vault.nonce()`, `amount <= balanceOf(vault, token)`.
6. caps: at most **3 per owner per UTC day** and **10 overall per UTC day**, both persisted (a `restores: { day, n }`
   field on `OwnerState`, the global one seeded from the store on boot like `createLimits` seeds from `starter` owners).
   Refuse when the funder is under `FUNDER_FLOOR_UQOR`.
7. owner `stage` must be `active` or `retired`; otherwise `409 { error: "not-active" }`. The reason is bookkeeping, not
   trust: the per-owner cap (step 6) lives in that owner's `state.json`, so an address the service never provisioned has
   nowhere to count against. Such an owner still has the self-hosted path (`pnpm cli sign-withdraw` + `#/recover` in a
   local build). For unknown addresses add a per-IP cap at the HTTP layer (`clientIp` already exists in `server.ts`) so a
   stream of rejected bodies cannot be used as a free oracle for `pqcVerify`.

Send: the **funder account** (`FUNDER_MNEMONIC`) opens a 1-tx window scoped to the vault (`openEvmWindowMsg` with
`allowedTargets: [vault]`, `maxTxs: 1`, the same hybrid broadcast the provisioner uses), then its ECDSA key sends
`vault.withdraw(to, token, amount, sig)` with `WITHDRAW_GAS`, waits for the receipt and returns
`{ hash, status }`. Not the guardian: a restore submit must never replace the guardian's live window and race a rescue
(chain fact 10: opening a window replaces an unexpired one).

Cost and accounting: ~0.225 QOR per submit (window) plus gas, paid by the funder, bounded by the caps above and by the
funder floor. Log one line per submit (`owner`, `vault`, `token`, `amount`, `hash`) — no code, no signature body.

Routes/errors: `400` malformed · `404` unknown owner · `409` not-active · `422 { error, check }` a named check of step
2-5 failed · `429` cap · `502` chain or broadcast failure. `retired` owners are revived by their next arm, not here.
Each new code gets an entry in `lib/hosted.ts` `PLAIN` (`recover-*`: vault, message, signature, nonce, balance,
cap, not-active) so `HostedError.message` stays a sentence a stranger can act on, and the restore screen prints it.

Client: `lib/hosted.ts` gains `submitWithdrawal(body)`; the restore screen calls it and shows the same success block the
Vault screen shows (`TxHash`, nonce before/after). If the request fails with `422`, print the named check with the same
words `CheckRow` uses.

  `#/restore`, use the `.txt` that Setup wrote, withdraw 1 fUSD to a fresh address, and confirm: the receipt is
  `success`, the vault nonce went up by one, `balanceOf(vault)` fell by 1e18, and the recipient's balance rose.
  Record the tx hash, the owner, the vault and the run id in `docs/EVIDENCE.md`.
- Replay: submit the same body again → `422 nonce` (the vault's nonce moved), never a second payout.
- Tamper: change `to` in the body and re-post → `422 message`.

### Acceptance

A person with only the downloaded `.txt` (account + code) and no wallet in the browser can move their vault balance to
a new address, in the hosted app, with an on-chain receipt in EVIDENCE, and no way for the service to redirect the
funds. The homepage FAQ answer stops saying recovery is on the roadmap.

### Risks and mitigations

| Risk | Mitigation |
|---|---|
| The service pays gas for anyone holding a valid signed withdrawal | Caps (3/owner, 10/day), funder floor, and the payout can only go where the owner signed |
| Signing outside a seed session weakens the key checks | `signWithdrawalInBrowser` refuses unless the key is registered **and** the derived key matches the on-chain key; the button enables only after the four restore checks and the six `checkWithdrawal` rows pass |
| A restore submit replaces the guardian's window | The funder submits, never the guardian |
| The code sits in a clipboard or file | Already stated (`CODE_POWER`); the restore screen repeats it and never stores the code |
| Scope creep into "wallet import" | Out of scope: the classical key cannot be restored from the code, and the screen must say so in one line ("this restores your vault, not your account's key") |
