# Threat model

Draft. Updated as the design and testnet findings change.

## What is protected
Assets the owner holds **on the EVM lane** of QoreChain (QOR and ERC-20s such as fUSD/fETH/fBTC).

**Out of scope:** native-lane transactions. QoreChain already requires a hybrid secp256k1 +
ML-DSA-87 signature for them, so a leaked ECDSA key alone cannot move native funds.

## Actors and keys
| Key | Holder | Can do |
|---|---|---|
| Owner ECDSA (secp256k1) | owner, **assumed leaked** | Send EVM txs while the owner's EVM window is open, up to its budget |
| Owner ML-DSA-87 | owner, offline Guardian Signer | Open windows (hybrid), link/revoke the agent, sign vault withdrawals |
| Agent ed25519 | Guardian agent | Signs incident reports. Linked to the owner's account with `allowedEvmCalls=[vault.rescue]`, `allowedDenoms=["uqor"]`: the chain refuses its direct token calls (tx `7E9B629F…`). It no longer performs rescues. The chain binds an authenticator key to ONE account (tx `422FE489…`), so each owner needs its own agent key; a report key can only ever speak for the account it is linked to |
| Guardian ECDSA + ML-DSA-87 (`GAS_MNEMONIC`) | Guardian agent | The vault's immutable `guardian`: calls `vault.rescue(token)` as plain EVM txs inside its own EVM window (vault as the only target), which it opens with its hybrid signature. Pays its own fees. Holds no owner funds |

## Threats

| # | Threat | Mitigation | Residual risk |
|---|---|---|---|
| T1 | Attacker with the leaked ECDSA key drains EVM assets | Scoped EVM window caps blocks, txs and value. The Guardian sweeps the remainder into the vault within ≤ 3 blocks | Spending rules do **not** bind the owner key (verified), so the **window budget is the only hard cap**. The first drain tx(s) before detection are lost |
| T2 | Attacker tries to withdraw from the vault | `withdraw` requires `pqcKeyStatus` registered + proven and a valid ML-DSA-87 signature over tag, chainId, vault, to, token, amount and nonce | None known. A quantum adversary would need to break ML-DSA-87 |
| T3 | Attacker replays an old withdrawal signature | Nonce is bound in the message and bumped before the transfer | |
| T4 | Agent keys are stolen or the agent is prompt-injected | **Guardian ECDSA key:** the vault lets it call `rescue` and nothing else, and `rescue` only moves the owner's approved tokens owner → vault. Its EVM window targets only the vault, and opening a new window needs its ML-DSA-87 key too. **Agent ed25519 key:** rule `allowedEvmCalls=["<vault>/<rescue selector>"]`, `allowedDenoms=["uqor"]` with no `erc20/` denom, so a direct `token.transfer` is refused (tx `7E9B629F…`) and a call through the vault cannot move tokens from the account either (tx `8508B568…`). The LLM has no say in actions | An attacker with the guardian ECDSA key can trigger needless rescues (funds still end up in the owner's vault) and burn the guardian's window budget and QOR. With the ed25519 key it can spend at most the uqor limits (1 QOR per tx, 3 QOR per day) of the owner's account on calls the rule allows. **Finding (Task 4C):** listing a token as `erc20/<addr>` in a spending rule lets the linked key call that token's `transfer`/`approve` directly, whatever `allowedEvmCalls` says; `denomLimits` only caps the amount (tx `CADB1412…`). That is why the agent no longer rescues through the authenticator lane |
| T5 | Attacker revokes the vault's allowance (`approve(vault, 0)`) before the rescue | Race. The Guardian reacts per block. Any `Approval(owner, vault, v)` with `v` below `maxUint256` (revoked or lowered, e.g. to 1 to dodge a check on 0) raises an alert-only incident, so the owner learns at once (Task 6B, incident `ea30c2ce…` for tx `0x1ca3b181…`) | Real risk, shown honestly in the demo. `setup` approves `maxUint256`, so a finite vault allowance is never the owner's own flow; a token that lowers a finite allowance inside `transferFrom` would raise false alerts (not the demo tokens). A rescue after the fact cannot fix it; only acting from the mempool could (roadmap, if diana exposes pending txs) |
| T6 | Attacker exhausts the window's tx budget to block the rescue | Not possible with the owner's key: the rescue txs run in the **guardian's own** window, which the owner's ECDSA key cannot use, open or close. The agent re-opens it when it runs low (checked every 30 s and before a rescue) | The guardian must stay funded with QOR for window fees and gas |
| T7 | False positive: Guardian sweeps on a legitimate owner transfer | Trusted list of wallets **and apps** (a dApp call moves tokens to a contract, so routers and pools must be listed; planned in Task 6B). Funds only move into the owner's own vault | Owner pays fees and needs one ML-DSA withdrawal to undo |
| T12 | Attacker with the leaked ECDSA key adds itself to the trusted list to switch the Guardian off, or reads it to learn which recipients and amounts avoid a rescue | The ECDSA key alone cannot reach the policy: it is a local file (`data/policy-<owner>.json`, 0600) edited only through the agent's API, which refuses to bind anything but loopback. Because any web page the owner opens can send requests to 127.0.0.1, every `/policy` request must carry a local `Host` (DNS rebinding), and `PUT /policy` also needs a loopback peer, an `Origin` from `DASHBOARD_ORIGINS` when one is sent (CSRF) and `Content-Type: application/json` (forces a CORS preflight); CORS on `/policy` never uses `*` (Task 6C, tests `test_policyWriteRejectedFromNonLoopback`, `test_serverBindsLoopbackOnly`) | Anyone with local access to the agent's machine, or a local process, can edit the policy. A hosted, multi-owner agent must require an ML-DSA signature for every policy change |
| T15 | Alerting or reporting delays the rescue: a slow LLM summary, a Telegram/webhook outage or a flood of `/health` calls | Only `rescue()` sits on the agent's single-flight path. The incident report (LLM summary, signature, publish) and the alerts run after it, unawaited, and a failing or hanging notifier is logged and skipped (5 s timeout per channel). `/health` serves cached values and makes no RPC call per request; the gas balance is read every 60 s off the rescue queue (Task 6C, `test_slowReportDoesNotDelayQueuedRescue`, `test_notifierFailureDoesNotBlockRescue`; diana: rescue 2 blocks after the drain with Telegram on, `docs/EVIDENCE.md` Task 6C) | Alerts are best effort: a channel outage loses that alert (the signed incident is still on the dashboard). Incidents may be appended out of detection order, so readers sort by `detectedAt`. The gas-low alert fires once per drop below `GAS_LOW_WEI` (default 0.5 QOR) |
| T16 | The dashboard trusts a lying or swapped agent: `GET /config` names another owner and vault (one whose linked key the agent controls), so forged incidents verify ✓, or a report body is swapped after it was verified | The dashboard checks every report in the browser against the chain, not the agent's word: ed25519 signature over the canonical body, the signing key linked to the owner and not revoked or expired (`fetchAuthenticators`), and each rescue's receipt and `Rescued` log from the vault. `/config` is checked on chain (`vault.owner()`, `vault.guardian()`), a mismatch shows a red banner and every report ✗. A ✓ is shown only for the exact body (id and sig) and config it was verified under; anything else shows as pending. The "tokens are safe" banner needs that report to verify. `/config` carries public addresses only (Task 6D, `verify.test.ts` `test_rejectsValidSigFromUnlinkedKey`, `verifyPolicy.test.ts`) | An agent that serves a consistent but different owner + vault pair is caught only by the owner reading the owner address in the top bar (a connected MetaMask account that differs is flagged). The window commands the dashboard shows carry `--expect <owner>`, so the CLI refuses to sign for another account |
| T13 | Approve or permit phishing: the owner is tricked into approving a spender, which then drains with `transferFrom` | A non-zero `Approval` from the owner to a spender outside the trusted wallets and apps triggers a rescue (Task 6B). `./demo.sh --phish` races it against a drainer that pulls from its own window (Task 7, `docs/EVIDENCE.md`): the rescue lands 1-2 blocks after the approval (2 in 4 of 5 runs, ~1.4 s blocks). A drainer that waits 2 blocks (its pull landed 4 blocks after the approval) got nothing (3/3). One that fires as soon as it sees the approval won 1 of 2: its pull landed 1 block after the approval; in the other run it landed in the same block as the rescue and was ordered after it only because the rescue tips 40 gwei and the demo drainer used the default tip | **A drainer as fast as the Guardian wins.** Both react to the same signal (the approval on the RPC), and the agent spends one extra read (balance, allowance, nonce) before it sends. A drainer that also outbids the rescue's 40 gwei tip would have won both worst-case runs. Only acting from the mempool (roadmap) could beat it. A permit (EIP-2612) signature emits no `Approval` until the drainer submits it, so the Guardian sees it only with the drain |
| T14 | The dashboard has the owner sign EVM txs in MetaMask (Task 6A), so the owner's ECDSA key sits in a browser wallet, a common place for it to leak | That key is exactly what T1 assumes leaked. A MetaMask tx lands only inside an EVM window that a hybrid (ML-DSA-87) tx opened, so a stolen browser key with no window moves nothing (refused at broadcast, chain fact 17). The dashboard never asks for a mnemonic or key and never opens a window itself | While the owner keeps a window open for the dashboard, a leaked key can spend within it (T1). Advise short windows sized to the planned txs, and closing it after |
| T17 | The owner window carries value for a gas-tank top-up, which a leaked ECDSA key can spend instead, and dashboard sends ("Rescue now", top-up) cost more of the window than planned | The owner window carries fees only by default. Value headroom is opt-in and exact: `pnpm cli window open --topup <QOR>` (at most 100 QOR) adds that amount and nothing more. The dashboard plans every send before MetaMask sees it: owner wallet on diana, config verified on chain, window live and scoped to the target, enough txs left, and `evmWindowCost(value + gas × fee cap)` within `remainingValue`, with the same fee cap passed to the wallet. "Rescue now" re-reads balance and allowance before each `rescue` and skips a token with nothing to move (Review Focus 1). A native QOR transfer to the guardian is the owner's own top-up, so the agent does not treat it as a trigger (Task 6E, `a4ed21d`; diana `0x7eec8c6d…`) | While a top-up window is open, a leaked key can send the headroom anywhere (T1). Keep it to the top-up amount and close the window after. A wallet that overrides the fee cap can spend more of the window than the dashboard checked |
| T18 | Browser onboarding (Protect, Task 6F): the vault deploy needs an UNSCOPED owner window (a window with targets refuses contract creation, chain fact 10), which a leaked ECDSA key can use against any target; or a vault is created for an owner with no ML-DSA-87 key yet, so a holder of the leaked ECDSA key registers THEIR key (a fresh account may register classically, chain fact 15) and later withdraws what the Guardian rescued | `pnpm cli window open --onboard` is bounded (1800 blocks, 5 txs, `maxValue` = 5 × 0.3375 QOR fees + an opt-in `--topup`) and prints an UNSCOPED warning; the Protect screen sizes it to deploy + 3 approvals + 1 top-up, shows `window close --expect <owner>` while it is live and does not call the account protected until it is closed or used up. Deploy, "I already have a vault" and the approvals are blocked until step 1 reads a registered, possession-proven ML-DSA-87 key for the connected wallet; the deploy uses the connected wallet as `owner_` and a guardian from the live agent's `/config` shown before signing, and the vault is remembered only after `owner()`/`guardian()` read back equal. `pnpm cli link` re-checks both roles on chain before signing (Task 6F; diana: deploy `0x469bba2a…`, onboarding window used up after 5 txs, `docs/EVIDENCE.md` Task 6F) | While the onboarding window is open a leaked key can send its whole budget (about 1.69 QOR plus top-up) anywhere (T1). The guardian address comes from the local agent's `/config`; `link` catches a wrong one only when `GUARDIAN_ADDRESS` is set |
| T19 | Fire drill (Task 6G): a web page the owner opens starts drills (each spends ~2 QOR of the funder), the drill's output carries a secret to the browser, or the drill disturbs the real owner's protection (a drill agent sharing the guardian would replace its vault-scoped window, chain fact 10, and race its EVM nonce) | `POST /drill` passes the same gate as `PUT /policy` (loopback peer, local `Host` against DNS rebinding, dashboard `Origin` against CSRF, `Content-Type: application/json` to force a preflight), and `demo.sh --drill` refuses without a separate `FUNDER_MNEMONIC`; every `/drill*` route checks `Host` and names only a dashboard origin in CORS, also on errors; one drill at a time (409). The drill runs `demo.sh --drill` with a minimal env and a SEPARATE drill guardian (`~/.config/qday/drill-guardian.env`, 0600, refused when it equals the real guardian, owner or funder), its own agent port (8788) and incidents file (the run dir), and no alerts. Output lines are redacted (12+ word runs, JSON word arrays, `MNEMONIC=`/`_SK=` lines) before they are stored or streamed; past runs come from `verdict.json` only, never `run.env`. The agent kills the drill's process group on exit, SIGHUP/SIGINT/SIGTERM and after 15 min, with SIGKILL 15 s after SIGTERM (diana: run `20261124T081242Z`, main agent window not reopened, `docs/EVIDENCE.md` Task 6G) | Any local process can still start a drill (loopback is trusted, like `PUT /policy`). A hex secret printed by some future component would not be redacted (no component prints one today). After a SIGKILL fallback the drill's own agent may keep running on :8788 until stopped by hand; the next drill then refuses before spending anything (drill port in use, `drill.lock`). A drill needs its own `FUNDER_MNEMONIC` (never the watched owner) and stops before fresh-owner when the drill guardian holds less than 0.5 QOR (`drill-guardian check`); one drill costs the drill guardian about 0.47 QOR, refilled with `drill-guardian init` |
| T20 | Turn off protection (Task 6E step 4): an attacker with the leaked ECDSA key uses the same `approve(vault, 0)` to switch rescues off, or the owner's unlink makes past reports unverifiable | The dashboard offers nothing an attacker could not already do with the leaked key, and the agent still raises an alert-only incident for every `approve(vault, 0)` (T5), whoever sends it. Unlinking the Guardian's key is a hybrid tx (`pnpm cli unlink`), so it needs the ML-DSA-87 key. While unlinked, every report shows ✗ (the chain no longer vouches for the key); re-linking the same key is accepted on diana (chain fact 21) and restores them | The owner turning protection off on purpose and an attacker doing it look the same on chain: only the alert tells them apart |
| T8 | Forged incident report on the dashboard | Reports are signed twice. The agent's ed25519 key signs them, and the dashboard checks that key is a currently linked, non-revoked authenticator of the owner on chain. Since submission gap 3 (2026-11-24) the vault's guardian account also co-signs the same bytes with QoreSign (eth_secp256k1 + ML-DSA-87), and the dashboard checks it in the browser with `verifyMessageWithChain` against the ML-DSA-87 key the guardian registered on chain, the signer bound to `vault.guardian()` (immutable). A changed report fails both (`CLASSICAL_SIGNATURE_INVALID`, `docs/EVIDENCE.md`) | **The co-signature can be dropped.** A report without one (older reports, or a co-signing failure) shows the check as n/a and can still verify on the ed25519 checks alone. Against a classical attacker that is enough; against a quantum attacker who recovers the agent's ed25519 key from its public key, an alert-only report with no co-signature would still show ✓ (the row says it rests on the classical key alone). Requiring the co-signature for every report would break the older ones; the roadmap is to require it from a cut-over the chain can vouch for. The guardian mnemonic and the agent's ed25519 key sit in the same env on the agent host, so against a host compromise the two signatures are not independent |
| T9 | Owner's registered PQC key uses a weaker algorithm than ML-DSA-87 | `GuardianVault` ignores `algorithmId` from `pqcKeyStatus`, like the workshop vault, and trusts the chain registry | Holds only if diana registers ML-DSA-87 keys alone. The demo owner's key was checked on diana (2026-11-20): `algorithmId` 1 = ML-DSA-87, 2592-byte pubkey (`docs/EVIDENCE.md`). If the chain adds another algorithm, a new vault must check the id |
| T10 | Spoofed `Rescued` events or griefing: a third party calls `rescue` to sweep the owner's approved tokens into the vault, or emits `Rescued` for a token it controls | `rescue` is callable only by the owner or the immutable `guardian` set at deploy (`NotAuthorized` otherwise; no setters). The agent reads `Rescued` logs emitted by the vault in its own rescue receipt, and agent and dashboard count only the fUSD/fETH/fBTC allowlist | Whoever holds the owner's or the guardian's ECDSA key can still call `rescue(anyToken)`: harmless, it only moves the owner's funds into the vault, but events must stay filtered (Tasks 4 and 6). A leaked guardian key cannot be rotated: redeploy the vault with a new guardian. Since Task 6E a native QOR transfer from the owner to the guardian is not a trigger (gas tank top-up), so an attacker holding both the owner's and the guardian's keys can move the owner's QOR (up to the window budget) through the guardian without a pre-emptive token rescue; any token drain still triggers |
| T11 | A drain is hidden from the watcher by an inconsistent RPC view | The watcher re-queries the last 3 blocks on each poll, so a node that lags by at most 2 blocks cannot make it skip a drain | The no-skip guarantee assumes one JSON-RPC batch is served by one node and that `getLogs` at "latest" is consistent with `eth_blockNumber`. The requery covers at most a 2-block lag, so an RPC gateway that splits a batch across nodes, or a lagging log indexer, could hide a drain. Mitigation: run the agent against a single trusted RPC node |

## Honest limits

Q-Lifeboat reacts to what lands on chain. It does not see the mempool, so it never stops the first transaction.

- **A one-shot drain is not stopped.** A `transfer` of the whole balance in one tx inside an open owner window is final before
  the Guardian sees it. The window's `maxValue` bounds QOR value and gas, not ERC-20 amounts, and spending rules do not bind
  the owner's own ECDSA key (chain fact 4). The real defence is the owner's EVM window being **closed by default**: with no
  window a leaked ECDSA key moves nothing (chain fact 17). The Guardian covers the time a window is open, a drain spread over
  several txs, and the gap between an `approve` and the `transferFrom` that follows it.
- **A drainer as fast as the Guardian wins the approval race** (T13). Against a drainer that pulls the moment it sees the
  approval the Guardian kept the funds in 1 of 2 runs, and that one only on the tip (same block, the rescue's 40 gwei tip
  ordered it first); a drainer that outbids that tip wins. Against one that waits 2 blocks it kept everything (3 of 3).
- **Revoking the vault's allowance is a race too** (T5): the Guardian raises an alert, it cannot undo it.
- **The agent runs on the owner's machine.** While it is stopped nothing watches; "Rescue now" on the dashboard is the manual
  fallback.

Roadmap: mempool watching and front-running where the chain exposes pending txs, a hosted agent with uptime guarantees, and a
withdrawal timelock on the vault (a delay the owner can cancel) as a second line behind the ML-DSA-87 check.

## Assumptions
- The owner's ML-DSA-87 key (mnemonic) is **not** compromised. It is the root of recovery.
- Testnet only. QoreSeal / confidentiality is out of scope: addresses, amounts and timing are public.
